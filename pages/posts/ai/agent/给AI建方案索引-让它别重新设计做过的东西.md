# 给 AI 建方案索引：让它别重新设计做过的东西

「按之前那个方案改一下。」这句话，我隔三差五就要对 agent 说一次。多数时候得到的回答是一个礼貌的「没有找到相关的方案文档」，然后它开始凭空设计一份新的——而那份「之前的方案」，就在我知识库的 plans/ 目录里躺着，标题、frontmatter、评审意见一应俱全。

问题不是它记性差，是「之前」这个词在它的上下文里没有指代。代码仓里它只看得见代码，知识库在另一个目录，它不知道有，就算知道也不会想到去翻。于是同一个需求隔一阵子就会被重新设计一遍：新方案和已落地的实现打架，老计划里记录的踩坑、被否掉的路、验收标准，全部重来一遍。

这件事靠提示词解决不了。prompt 里写「动手前先想想有没有做过」，它想想，说没有，继续设计。真检查它有没有找过？找过，ls 了两眼，没翻到。38 份计划散在 9 个仓库的三级目录树里，靠文件名猜，和大海捞针没有区别。

所以我没有继续调 prompt，而是给知识库配了一个 322 行的 Python 索引器（`plan_index.py`），外加一条命名纪律、一条流程规则。没有向量库，没有 embedding 服务，没有常驻进程。现在的实际效果是：我在任何一个代码仓里对 agent 说「这个需求怎么做」，它在回答之前会先跑一次定位——命中就直接读全套上下文动手，没命中才来问我。

以下机制描述基于 2026-09-18 的版本，语料为当日快照：38 份设计计划、9 个仓库、5 份衍生评审稿，时间跨度 2026-08-11 到 2026-09-16。文中所有检索结果均为当日实跑，没有演示数据。

## 一、为什么不用向量库

第一个被否掉的就是向量方案。三个理由，都跟场景有关。

38 份文档，单人维护，主题集中在我自己这几个业务仓上。这个规模下 embedding 的优势（语义泛化）体现不出来，劣势（不可解释）反而是致命的。因为定位这个动作需要的是**判定**，不是排序。我要的输出是四选一：就是它（直接干）、可能是这几份之一（列出来问我）、有相近但不确定（问一句）、没有（问要不要新起一份）——每个判定对应不同的后续动作。相似度 0.87 给不出这个判定。

第二个理由是要能调试。误命中总会发生，发生了我要能在一分钟内看清「为什么是它」：命中了哪几个词、每个词值多少分、哪个字段给的权重。bigram + IDF 的打分过程全程透明，向量距离不是。

第三个理由是维护。向量方案要么常驻服务，要么每次查询先算 embedding；索引器是每次查询实时扫目录——38 个文件毫秒级扫完，新增一份计划立刻可搜，根本不存在「索引没更新」这个故障模式。

小语料加判定义务，简单检索反而是对的工具。

## 二、中文没有分词，那就 bigram

检索的第一步是把 query 切成词。中文没有天然空格，装分词器？多一个依赖，而且我这个语料里的专业词——devId、sjs、DP、objectKey——通用分词器切不好。干脆不切：所有连续汉字两两一组滑窗，这就是 bigram。

看一次实跑的命中词集合，query 是「快捷功能拖拽排序松手闪烁」：

```
命中: 功能 快捷 手闪 拖拽 捷功 排序 松手 能拖 闪烁
```

注意手闪、捷功、能拖这三个碎片——单看没有意义，是滑窗切出来的边角料。但它们不需要有意义：真目标是那份《快捷功能拖拽松手闪烁修复》，它和 query 共享九个 bigram，碎片对齐得足够多，本身就是强证据。bigram 的代价是引入噪声碎片，好处是零依赖、零词表、召回稳。这次查询 cov=0.81、mass=16.7，判定 hit。

命中也不是一视同仁，字段有权重：标题和 slug 最值钱（1.0），需求目录名 0.8，tags 0.7，章节标题 0.5，正文最不值钱（0.3）——命中的位置越接近「这份文档是什么」，越可信。

再往上是 IDF。「方案」「计划」「优化」这类 bigram，38 份里几乎每份都有，对区分毫无贡献，公式自动把它们压到接近零。我不需要维护停用词表，也不需要预知哪些词该停用。这是搜索引擎 1970 年代就会的手艺，在这个规模上，够用。

## 三、一个分数不够：cov 和 mass

整套设计里最值得说的决定：打分给的是两个独立的量，不是一个分。

**cov，贴合度。**分母只统计语料里存在的 query 片段（文档频率大于 0）。这是为了支持一个重要用法：query 直接用用户原话。用户说「的时候换绑判定算不对」，「的时候」在任何计划里都不出现，不进分母，不拉低贴合度——于是流程规则里可以明写「不要把用户的话翻译成规范术语再查」，翻译这一步会引入 agent 自己的偏差，而 bigram 的设计已经保证原话可用。

但只有 cov 会翻车，翻车方式还很反直觉：问一个语料里完全没有的主题，cov 反而可能很高。因为内容词全被 df=0 排除之后，分母里剩下的全是「功能」「的车」这类到处乱撞的噪声 bigram，随便撞上一两个，比例就上去了。语料越不相关，分母越空，撞上的比例越高。

**mass，证据量。**命中的全部 IDF 加权和，挡的就是上面这个坑：贴合度再高，证据总量不够就是没找到。

一组实测对照（2026-09-18）：

| query | cov | mass | verdict |
|---|---|---|---|
| 快捷功能拖拽排序松手闪烁 | 0.81 | 16.7 | hit |
| 全生命周期里程换绑判定 | 1.00 | 20.4 | hit |
| 拖拽排序 | 1.00 | 6.1 | hit |
| K8s 集群弹性伸缩 | 0.50 | 1.5 | **not_found** |

最后一行就是 mass 的价值。语料里没有任何 K8s 相关计划，唯一沾边的是「k8s」这个词出现在某份 Python 重构计划的依赖清单里。cov=0.50，看起来「一半相关」；实际上唯一证据是一个到处飘的词。mass=1.5，低于阈值 1.8，判 not_found。没有 mass，这一条会被当成「找到一份差不多相关的方案」交给 agent，然后它兴冲冲地去读一份 Python 重构计划，把不相关当成相关——空命中比查不到危险得多。

## 四、verdict 阶梯：让 agent 知道什么时候闭嘴问人

打分之后是判定。判定是个阶梯，不是二值：

| verdict | 条件 | agent 该做什么 |
|---|---|---|
| hit | cov≥0.55 且 mass≥4.0，且对第二名断层≥1.4 倍 | 直接读，不要问用户 |
| ambiguous | 几份都够贴合、断层不够 | 列候选，问一句选哪份 |
| weak | 有相近的但不过线 | 给 top1，问「是这份吗」 |
| not_found | mass 不足 | 问：有文档地址吗，还是新起一份 |

另有一条灰区通道：cov 不达 0.55 但 mass≥4.0、且对第二名断层 2 倍以上，也判 hit——贴合度在灰区时，证据量和断层可以补位。这些阈值（0.55 / 0.30 / 4.0 / 1.8）是用我自己这 38 份语料调出来的，换语料要重调，不是普适常数。

「拖拽排序」那次实跑展示了断层的用途：语料里其实有四份拖拽相关计划，top1 的 mass 是第二名的 2.9 倍——这时候没必要问用户，断层本身就是答案。断层不够就是 ambiguous，老老实实列候选。

两条配套机制比阈值更重要。一是**同仓优先**：仓库键取当前目录的 git 顶层名，排序键是（同仓，分数）——在业务仓里问「串货」，本仓计划天然压过其他仓的同名计划。二是前面说过的**原话直查**。

阶梯真正的价值在防两件事：防 hit 时多嘴（明明定位到了还反问「你是说这份吗」，白问一次），防 not_found 时不吭声（默默拿相似度最高的凑数）。流程规则写死了：只有 weak / ambiguous / not_found 才准反问，且只问一次，不连环追问。

## 五、命中之后的三件事

索引只负责「找到」，找到和「用对」之间还隔着三件事，都写进了命中后的必做清单。

**第一，读评审稿。**每份计划可能带一份 tech-review，评审意见可能已经推翻计划里的某条主张——只读计划不读评审，会拿着被否过的设计继续做。索引在数据层面处理了这个坑：评审稿不参与排名（它们会和母计划抢第一名），而是挂到母计划的 review_docs 字段上，命中母计划时一并带出来。

**第二，读依赖文档。**计划 frontmatter 的 depends_on 指向同一需求目录下的技术方案、对接文档，按点名优先读；标了「已不存在」的不要猜替代文件。

**第三，也是最容易被跳过的一步：核对 status 与代码现状。**status 是写文档那一刻的快照——draft 可能已经部分落地，implemented 可能已经被重构掉。所以规则要求按验收标准逐条回代码核，核的方式沿用我给自己定的另一条纪律：查调用方、查配置门槛，不是只读方法体就断言「已实现」。核对出不一致，先如实报告差异，再问是按计划补齐还是按现状改计划。

三件事做完，定位才成立。它交付的不是一份文档路径，而是这样的报告：

```
定位到方案：PLAN-2026-09-02-003《换绑判定里程改为车辆全生命周期》(status=draft)
已读：计划本体 + docs/01-技术方案.md §4.4 + docs/04-绑定前校验对接文档.md §5.2
代码核对：AC-001~003 已落地，AC-004 未实现
```

「按之前的方案改」到这一步才真正成立：把几个月前那次决策现场——踩过的坑、被否掉的路、评审时吵过的点——完整重建进上下文。

## 六、维护成本在哪

脚本本身零维护：find 实时扫目录，没有「更新索引」这个动作；给人看的 INDEX.md 快照不参与匹配，坏了都不影响检索。另有一个 inject 子命令，把全量计划清单压成几十行，在会话启动时注入——所以多数时候 agent 不跑 find 也知道知识库里有哪些计划，find 留给需要精确定位的时刻。两层配合：注入给全局感，find 给判定。

真正的成本在纪律：文件必须叫 `PLAN-YYYY-MM-DD-NNN-<一句话slug>.md`，frontmatter 必须有 doc_id、title、status。标题和 slug 是检索的主要语料，命名一乱，命中就散。这套纪律原本只是为了让目录能看，现在成了检索质量的下限——算是以命名换索引，一次付清。

顺带一个副产品：新计划放进目录立刻可搜，「沉淀计划」这个动作的摩擦几乎为零。索引越好用，计划写得越勤；写得越勤，索引越有用。这个正循环是目前整套东西里我最满意的部分。

## 我们能做的

- 「先找再动手」要写成流程规则，别指望模型自觉。规则一句话就够：在代码仓里描述一个要做的东西且没给文档路径时，先跑定位器，按 verdict 行事；hit 不许反问，not_found 不许凑数。
- 个人小语料（几十到几百份），bigram + IDF 的透明打分完全够用。向量库在这个规模是负资产：给不出判定，还不可调试。
- 给「没找到」一个显式状态和显式动作。空命中比查不到危险得多——它会拿着一份不相关的文档信心满满地继续。
- 命中之后强制核对文档与代码现状。文档是快照，不是事实；这条不进规则，索引找到的也会被用错。
