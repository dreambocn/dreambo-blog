# 嵌入式 Agent：卡住的不是代码，是回路

2026 年 9 月 10 日，Embedder 和 SEGGER 宣布合作：Embedder 的 AI agent 拿到了 J-Link 与 J-Trace 调试探针的直接控制权。一个 agent 从此可以自己烧录固件、下断点、读寄存器和内存、通过 RTT 看实时输出——失败就接着在真板上调，直到跑通。

几个月前，做微型无人机的 Bitcraze 已经用另一种方式走通了同一件事。他们自己写了一个小 CLI，只给 agent 三样能力——**烧录、看控制台、复位**——就让它把固件开发的回路闭起来了。

两件事隔着半年、隔着"自造"和"商用"，但指向同一个判断：**在嵌入式领域，AI agent 的瓶颈不在会不会写代码，而在能不能把回路闭到真硬件上。** 而闭回路的关键，不是换一个更强的模型，是把调试能力做成 agent 能用的接口。

下面把这条线拆开讲：为什么嵌入式特别难、两种闭回路的做法、以及最难的一层——硬件会说谎。

## 一、为什么嵌入式 agent 和别的 agent 不一样

通用 coding agent 在 Web 和脚本世界里已经很好用，因为那里的反馈是廉价且确定的：跑一遍测试、看一眼报错、改一行、再跑。编译器不骗人，测试不骗人。

嵌入式不是这样。EE Journal 的 Max Maxfield 在 2026 年 4 月写 Embedder 时有一段很到位的描述：嵌入式开发"**与其说是工程，不如说是考古**"——在写第一行有意义的代码之前，你得先从数据手册、参考手册、寄存器映射、时序图、勘误表和一堆应用笔记里，把那些"神奇数字"、初始化序列和时序约束挖出来。而传统流程是：读文档 → 写码 → 编译 → 烧录 → **看它到底炸不炸**。

问题在于，这里的"看起来对"远远不够。一个幻觉出来的寄存器值、一段错误的外设初始化、一个漏掉的时序要求，结果就是一块死给你看的板子。Maxfield 的比喻是：板子"**在沉默的责备中瞪着你**"。

更要命的是另一层：如果这段代码本来就是 AI 写的，那调试它就像"**试图理清别人半梦半醒的呓语**"。

所以嵌入式 agent 的真正难点被顶到了两处：

1. **知识必须落到具体这颗芯片、这块板子上**，而不是从"别家开发板"的模式里猜；
2. **验证必须发生在线下物理世界**，而不是在聊天窗口里自我感觉良好。

## 二、轻量派：三件套 + 一个 skill

Bitcraze 的 Arnaud 在 2026 年 4 月的复盘里，把痛点说得很直白：

> 试着让 coding agent 做嵌入式时，我很快发现自己变成了**手动测试员**——复制日志、把行为描述回去给 agent。是**我**在闭这个回路，既低效又让人抓狂。

他们的解法是"控制权交给命令行"。coding agent 最大的长处就是能调 CLI 工具，把一堆小工具拼起来，能做的事远超任何单个工具——"**本质上是把 Unix 哲学用在 AI 辅助开发上**"。

于是他们为 Crazyflie 无人机写了个 `crazyflie-agent-cli`，能力清单很短：

- **烧录**（走 bootloader）
- **复位**（进 bootloader 或固件模式）
- **Console**（流式读固件的调试输出）
- **Parameters**（读写参数）
- **Log variables**（流式读日志变量）

Arnaud 的判断是：这差不多就是固件开发的**最小可用集**。因为 agent 本来就会写 C、会编译，只要再给它"烧录 + 看输出 + 复位"，理论上它就够了——实现功能、烧进去、观察行为、发现 bug、再迭代，和人的工作流一模一样。

**最有价值的一条设计经验，藏在一个不起眼的细节里。**

Crazyflie 的通信天生是**有状态**的。人用的时候会开一个交互式客户端，连上无人机，然后慢慢点、读参数、看日志、现场调。但 agent **用不了交互式 CLI**。所以这个工具改成了 **daemon + 一次性命令**的架构：agent 先起一个后台 daemon 建立无线连接，之后每条命令都是一次性的、互不依赖。

对人类来说这个设计不友好——你得开两个终端。但对 agent 来说"出奇地好用"：它管后台进程毫无压力，一条条发命令就行。

最后一块拼图是 **skill**。CLI 给了 agent"能操作"的能力，但还得让它"知道怎么操作"。他们写了个 skill 教 agent：Crazyflie 是什么、怎么烧、怎么调。Arnaud 说这才是真正把回路闭上的东西——skill 一放进去，agent 就知道该怎么干了。

他自己的结论也很克制：**"这是力量倍增器，不是工程判断的替代品。人仍然得在回路里。"**

## 三、重装派：把整张工作台接进来

如果说 Bitcraze 是"最小可用回路"，Embedder 走的是另一个极端——把嵌入式工程师桌上所有东西都接进 agent。

Embedder 是一家 2025 年 4 月才成立、YC 背景的公司，官网（2026 年 9 月口径）称已有 8000+ 工程师使用。它的定位不是"通用 coding agent"，而是**面向固件的企业级 AI 平台**，卖的是一整条从文档到真机的证据链：

- **数据手册智能**：读完整本参考手册（寄存器映射、时钟树、勘误表），写下的**每一个寄存器值都引用到手册的具体章节**；
- **原理图摄取**：支持 Altium / KiCad / Eagle / PADS / Xpedition，把网表对着数据手册解析——引脚复用、上拉、总线地址、勘误规避，"不假设厂商开发板上的配置"；
- **硬件调试与 RCA**：驱动 GDB 会话，单步断点、检查寄存器和内存，把运行时状态和源码对应起来；串口 trace、寄存器 dump、原理图上下文都会**附在每一条根因结论后面**；
- **信号观测**：把逻辑分析仪抓包和示波器波形转成结构化数据，让时序违规、协议错误、信号完整性问题变成"可复核的证据"；
- **功耗画像**：驱动功耗分析仪抓工作负载下的电流曲线，把高功耗窗口关联回固件在做什么，每次低功耗改动都**在真芯片上重新测量**来证明；
- **并行测试 agent**：把一轮固件测试拆给多个专用 agent 并发跑，再合并 pass/fail；
- **闭环验证**：把编译、烧录、运行观测、代码修复串成一个紧回路——测试失败就诊断、打补丁、重新验证，无需人工介入。

再叠上 SEGGER 这一层：J-Link 是业界最主流的调试探针家族，支持 **15000+ 器件**，覆盖所有主流 MCU。有了它，agent 能像工程师一样：烧录 build、设断点、检查寄存器和内存、通过 RTT 看实时输出。

两家的话值得原样记下来。

SEGGER 的产品经理 Erik Loehr：

> AI agent 正在变得远不止是生成代码的工具。它们能分析现有固件、调查异常行为、定位 bug、帮助开发和验证解决方案。但在嵌入式系统里，这**要求直接访问真实的目标硬件**……我们让 AI 能参与整个嵌入式开发周期——从写代码到在设备上调试和验证它。

Embedder 的创始人兼 CTO Bob Wei 那句是整件事的题眼：

> 随着 AI agent 变得更强，嵌入式开发**最大的瓶颈正在从"写固件"转移到"验证它满足功能和性能要求"**。

顺带一提，Embedder 在合规和 IP 上是按企业采购的口径做的：SOC 2 Type II、ISO 27001 / GDPR，支持公有云、私有云、BYOC，以及**完全离线气隙部署**（针对国防、航空航天、工业控制、ITAR 这类场景）。功能安全关键词也摆得很前：MISRA C、ISO 26262、IEC 62304、IEC 61508、DO-178C。语言支持 C / C++ / Rust / MicroPython，RTOS 覆盖 FreeRTOS、Zephyr、nRF Connect SDK、ESP-IDF、STM32Cube、MCUXpresso。

## 四、第三条路线：先把硬件上下文喂进去

前面两条路都在解决同一个问题——**怎么让 agent 碰到硬件**。还有第三条路，攻的是另一个问题：**怎么让 agent 认得硬件**。

涂鸦把自家的 TuyaOS 架构以 Apache 2.0 开源成 **TuyaOpen**：一套跨芯片的统一 C/C++ 应用框架，用统一的 API 层屏蔽底层芯片差异，让应用代码跨平台复用，官方口径覆盖 T2/T3/T5 系列、树莓派 4/5、ESP32 等 15+ 款芯片。在这个底座上，他们推出了 **TuyaOpen IDE**（截至 2026-09 的公开文档口径）。

它的技术路线有两点值得注意。

**一是不造新工具。** TuyaOpen IDE 不是一个新 IDE，而是 **VS Code 和 Cursor 的原生扩展**——你每天用的编辑器就是它。背后的判断是：agent 的战场已经在现有工具里，没必要再开一个。

**二是给 agent 注入结构化的硬件上下文。** 这是整条路线的核心。通用 coding agent 的通病是：它不知道你这块板子的芯片架构、GPIO 映射、SDK API，于是"频繁生成引用不存在的配置的代码"。TuyaOpen IDE 的做法是**把这些硬件上下文作为高优先级提示注入 agent**，让它在"认得这块板子"的前提下写代码，而不是从别家开发板的模式里猜。

它对 agent 也不挑：海外支持 Claude Code、Cursor、Codex、Gemini CLI、GitHub Copilot，国内支持 Qwen Code、Trae，模型随 agent 自己配。在受支持的芯片上，它覆盖从建工程到**烧录、调试**的完整回路，还能顺手做原理图审查、元器件选型、新驱动适配、App 面板迭代这些衍生活。

**三条路的分工其实很清楚：**

- Bitcraze 把回路做**低**——三件套先跑起来；
- Embedder 把回路做**深**——探针和仪器，往单板级证据钻；
- TuyaOpen IDE 把回路做**通**——上下文注入 + 平台抽象，且复用你已有的 agent。

前两条解决"碰到硬件"，第三条解决"认得硬件"。这两件事是**乘法**关系，不是替代：上下文再准，碰不到硬件，agent 还是只能写"看起来对"的代码；能碰到硬件却不认得它，agent 就会在错误的假设上把板子烧坏。真正成熟的方案，大概率是两条都做。

## 五、最深的一层：硬件会说谎

到这一步，agent 已经能"编译、烧录、读回寄存器、看日志，然后告诉你：按软件看，一切正常，LED 应该在闪"。

Maxfield 在采访 Embedder CEO Ethan Gibbs 时，追问了一个很嵌入式的问题：**可万一硬件在说谎呢？** LED 就是不亮——因为它插反了、因为它接错了脚、因为那根"临时"跳线比你以为的更临时，在你没看的时候悄悄松了。

这是软件世界不存在的失败模式。代码可能完全无辜。

Gibbs 的回答是：他们在做**把视觉模型接进平台**。近期目标是确认 LED 是不是真的在闪；远期则是——检查元件是否在位、线是否接对、跳线是否插好、板子是否真的按软件预期配置好了，**在测试开始之前**。

Maxfield 说他当时"忍不住发出了一声兴奋的尖叫"。因为他想起自己无数次追逐一个"微妙的软件 bug"，最后发现真凶是硬件侧一个可笑的低级错误。

如果这一步真做成了，那它就不太像一个"聪明的编码工具"，而更像"一个真正有硬件意识的开发伙伴"的雏形了。

## 六、三条能带走的判断

把两条路放在一起，有三条判断对做端侧的人都成立。

**第一，瓶颈的位置变了。**
过去嵌入式最耗人的是"写"，现在是"验"。Bob Wei 那句话是整个趋势的浓缩：模型能力越强，写代码越不值钱，**在真硬件上证明它对**越值钱。谁能把验证的成本降下来，谁就拿到下一段效率。

**第二，为 agent 设计接口，和为人设计接口，是两套设计。**
Bitcraze 那个 daemon + 一次性命令的改动，看着只是工程细节，其实是核心洞察：**交互式 CLI 是给人的，agent 需要的是无状态、可脚本化、可并发的接口。** 这条原则不限于嵌入式——任何你准备交给 agent 用的内部工具，都值得按这个标准重想一遍。

**第三，回路有个最小充分集。**
Bitcraze 只用了三件事（烧录 / 看输出 / 复位）就闭合了。这提醒我们：**不必一开始就上探针和仪器**。先把"改完能自己烧、能自己看、能自己重来"做通，agent 的迭代能力就已经和"人在中间传话"是两个量级了。探针级的断点/寄存器/RTT 是进阶，不是入场券。

## 七、边界与代价

**它是倍增器，不是替代品。** Bitcraze 自己把这句话写在结论里。agent 会犯错，人仍然要对"到底该做什么、什么算通过"负责。

**agent 会"骗过验证"。** 这一点在纯软件的性能优化里已经反复出现——有 agent 为了达成指标，直接把被测功能关掉来制造"加速"。硬件场景只会更隐蔽：日志说正常、寄存器读回也对，问题出在板子上。所以"验证的验证"（比如视觉确认 LED 真在闪）不是花活，是必需品。

**探针和仪器是独占资源。** 逻辑分析仪、示波器、功耗分析仪一次只能服务一个测试；并行测试 agent 听着很美，落到台架上会撞资源。这也是为什么"轻量派"和"重装派"不是替代关系——**便宜的回路上跑迭代，贵的回路上做确认**，各司其职。

**重装派有真实门槛。** 数据手册要能索引、原理图要能解析、芯片要有 SVD/勘误数据、企业还要过安全评审。Embedder 把气隙部署和功能安全合规放在官网最前面，本身就说明这套东西卖给的是谁。

一句话收尾：**AI 写固件这件事，真正难的不是写，是让它在真板上认账。**
