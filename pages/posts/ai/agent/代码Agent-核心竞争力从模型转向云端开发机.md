# 代码 Agent 的核心竞争力，正在从模型转向云端开发机

最近看到一篇文章，作者没有比较哪个模型的跑分更高，而是钻进 Claude Code 和 Instinct 的运行环境里，去看一个代码 Agent 到底住在哪里、怎么拿到工具、文件放在哪、会话结束后什么还能留下。

这个角度很重要。

我们习惯把代码 Agent 想成一个模型加上一组工具：模型负责思考，工具负责读文件、改代码、跑命令。但当 Agent 开始承担更长、更复杂、更需要反复执行的任务后，真正决定它能不能把事情做完的，往往不是模型单轮回答得多漂亮，而是它背后有没有一台可靠的云端开发机。

以下内容以 2026-09-08 能查到的公开资料为准。关于 Claude Code 和 Instinct 内部运行环境的部分，来自作者对实际沙箱的观察，不代表所有产品都采用同样的实现。

---

## 一、代码 Agent 不只是聊天框里的模型

普通聊天机器人的工作方式很容易理解：

```text
用户提问 → 模型生成回答 → 用户决定下一步
```

代码 Agent 的循环完全不同：

```text
读取仓库 → 修改文件 → 执行命令 → 观察输出 → 继续修改
```

这条循环里，模型只负责其中一部分。它需要一个可以持续工作的执行环境，至少包括：

- 一个真实的文件系统；
- 能安装依赖、运行编译器和测试的进程环境；
- 能访问必要资源、又不会随便访问宿主机的权限边界；
- 可以保存工作区和任务状态的持久化存储；
- 出错后能重新进入、继续执行的会话机制。

模型强不强，决定它有没有机会找到正确答案；开发机稳不稳，决定它能不能把答案变成可验证的结果。

这两个能力以前经常被混在一起，因为 Agent 都在本地终端里运行。开发机是现成的，模型只需要调用 Bash、编辑器和测试命令就行。云端化之后，执行环境不再是默认存在的背景，而变成了产品本身。

## 二、第一层变化：Agent 需要一台真正的电脑

文章对 Claude Code 运行环境的观察很有代表性。

它不是在一个普通的 HTTP 请求里调用几个远程函数，而是在一个 Firecracker microVM 里启动自己的控制进程。这个进程作为虚拟机里的 PID 1，负责挂载磁盘、接收宿主机控制，然后再启动 Agent harness。

虚拟机里的磁盘也不是简单的临时目录：

- 可写磁盘属于用户，工作内容可以跨回收保留；
- Agent 自己的运行文件放在只读磁盘上；
- 宿主机通过 vsock 驱动虚拟机，而不是给用户环境开放普通入站网络；
- 模型推理在虚拟机外完成，运行环境通过 HTTPS 把请求发到模型服务。

这套设计表达了一个产品判断：**机器可以销毁，工作区不能随便丢；模型可以在云端推理，执行环境必须靠近代码。**

如果只把 Agent 理解成 API 调用，这些细节都像基础设施实现。但如果 Agent 要连续工作几个小时，它们就是用户体验：

- 任务被暂停后能不能继续；
- 依赖装到一半后能不能恢复；
- 多个 Agent 能不能互相隔离；
- 某个命令失败后，前面的修改还在不在；
- 用户离开电脑后，任务能不能继续跑。

所以代码 Agent 的第一项基础能力，不是“会不会写函数”，而是“有没有一个不会轻易消失的工作空间”。

## 三、第二层变化：沙箱不只是安全功能，也是执行能力

本地 Agent 的权限问题通常表现为一个弹窗：是否允许它执行这个命令。

云端 Agent 则必须把权限设计成基础设施，因为它运行的不是用户当前打开的终端，而是一台可能持续运行、可以联网、可以创建进程的远程机器。

一个合格的云端开发机至少要回答四个问题：

1. Agent 能读写哪些文件？
2. Agent 能启动哪些进程？
3. Agent 能访问哪些网络资源？
4. Agent 的命令失败或越权时，系统是阻止、告警，还是直接让任务结束？

这四个问题很难用一个“安全模式”解决。文件写权限、进程隔离、网络出口和凭证管理，实际上是不同的安全边界。

DeepSeek Harness 的公开实现也说明了这一点。它在不同平台上分别使用 bubblewrap、Landlock、macOS Seatbelt 或 Windows 受限令牌来隔离执行环境，还明确承认某些平台的隔离能力是 partial，而不是把所有环境都包装成同样可靠。

这比一句“我们有沙箱”更有价值。因为 Agent 产品真正需要的是**可解释的执行边界**：用户知道它能做什么，系统知道它实际做了什么，出问题后还能重建当时的状态。

沙箱因此不只是防止 Agent 破坏电脑。它也决定 Agent 能不能放心地运行自动化任务。边界过松，用户不敢授权；边界过紧，Agent 连构建和测试都跑不完。

## 四、第三层变化：长期记忆可能先从 Git 仓库开始

Instinct 的设计里有一个很朴素、但很值得注意的选择：它把 Agent 的长期记忆放在 `/memory` 目录中，目录本身是一个 Git 仓库，内容是 Markdown 文件，再把这个仓库持久化到对象存储。

机器是临时的，记忆仓库是长期的。

这套方案没有把“记忆”神秘化。它就是一组可以查看、修改、提交和回滚的文件，并通过目录区分实体、对话、时间线、工作流和知识。Agent 作为 Git 作者，把自己的记忆写下来并提交。

它的优点很明确：

- 文件对人可读；
- 变更可以 diff；
- 错误记忆可以回滚；
- 用户可以审查 Agent 到底记住了什么；
- 工作区、记忆和执行历史可以使用相近的工程工具管理。

这不代表 Git + Markdown 就是记忆系统的最终答案。它同样有检索效率、冲突解决、隐私保护和过期淘汰的问题。但它提醒我们，Agent 的长期记忆首先是一个**持久化和治理问题**，其次才是向量检索问题。

如果连“记住了什么、什么时候写入、谁改过、能不能撤销”都回答不了，换成更复杂的向量数据库也不一定会让记忆变得可靠。

## 五、模型、执行环境和记忆，正在拆成三个系统

从这些实现可以抽出一个更稳定的架构：

```text
模型：决定下一步做什么
执行环境：真正读文件、跑命令、修改系统
持久层：保存工作区、会话、记忆和审计记录
```

三者不一定由同一家公司提供，也不一定运行在同一台机器上。

Claude Code 的运行环境把 Agent harness 放进微型虚拟机，模型推理则通过外部服务完成。Instinct 的沙箱更像一个执行表面：命令在沙箱里跑，工具调用和模型控制更多在后端完成。DeepSeek Harness 则把文件系统、进程、子 Agent 和沙箱都抽象成可以替换的 provider。

共同趋势是：**Agent 不再是一个模型包着几个函数，而是一个由模型、执行面和持久层组成的分布式系统。**

这也解释了为什么“换一个模型”有时没有想象中那么重要。只要任务需要读写真实仓库，模型效果还会受到下面这些因素的影响：

- 工具返回结果是否完整、可定位；
- 上下文压缩后有没有丢掉关键状态；
- 工作区是否能在长任务中保持一致；
- 测试和构建环境是否稳定；
- Agent 能不能并行创建隔离工作区；
- 失败后有没有可靠的恢复点；
- 每一次模型可见输入是否都能从日志里重建。

模型只是决定上限的一部分。执行环境决定这个上限能不能兑现。

## 六、为什么“云端开发机”会成为竞争焦点

本地运行 Agent 的最大优势，是开发环境已经存在：代码、终端、密钥、依赖、浏览器和各种工具都在用户电脑上。

但本地也有天然限制：

- 电脑关机，任务就停；
- 长任务会占用本地 CPU、内存和网络；
- 并行 Agent 容易互相污染工作区；
- 把任务交给手机或网页后，原来的执行环境不一定还能接上；
- 团队很难统一每个人的工具版本和权限边界。

云端开发机解决的不是“把终端搬到网页里”这么简单，而是把开发环境做成一种可以调度的资源：

- 按任务创建；
- 按项目恢复；
- 按权限隔离；
- 按事件审计；
- 按需销毁和回收。

对个人来说，它意味着 Agent 可以在你睡觉时继续跑。对团队来说，它意味着每个 Agent 都可以在一台标准化、可审计、可回滚的机器上工作。

这时产品比较的重点自然会变化。用户不只会问“你用的是什么模型”，还会问：

- 任务是否能后台运行？
- 有多少并行工作区？
- 能不能直接访问完整仓库和构建环境？
- 网络和凭证怎么隔离？
- 任务中断后能不能恢复？
- 生成的代码能不能从日志重放？

这些问题的答案，最终都会落到云端开发机上。

## 七、但云端化也带来新的代价

云端开发机不是免费升级，它把本地环境里隐含的问题全部显性化了。

### 1. 数据边界变复杂

代码、构建日志、环境变量、工具调用和模型上下文都可能离开本地电脑。企业需要知道哪些内容进了模型，哪些内容只停留在沙箱，哪些凭证可以被 Agent 使用。

### 2. “能执行”不等于“可审计”

如果模型看到过一段系统自动注入的上下文，但日志里没有记录，任务结束后就很难解释它为什么做出某个决定。对 Agent 来说，模型输入、工具调用、文件变更和外部副作用都应该成为可重建的事件。

### 3. 恢复成本可能高于推理成本

一个模型调用失败，重新请求一次就行；一个云端开发机状态不一致，可能要重新安装依赖、恢复工作区、寻找上一次有效快照。执行环境的状态管理，会变成 Agent 产品的长期成本。

### 4. 沙箱隔离会影响实际生产力

过于严格的权限会让 Agent 无法安装依赖、访问测试服务或启动浏览器；过于宽松的权限又会让用户不敢把真实项目交给它。好的产品不是简单地追求“最安全”，而是让每一层权限都能解释、配置和回收。

## 八、接下来该怎么比较代码 Agent

以后看一个代码 Agent，我觉得可以少问一句“它背后的模型是谁”，多问下面几件事：

1. 它有没有独立、持久的工作区？
2. 工作区能不能被快照、恢复和审查？
3. 文件、进程、网络和凭证的边界是否分开？
4. 它能不能在后台运行，不依赖用户一直开着终端？
5. 多个 Agent 能不能使用隔离的 worktree 或虚拟机？
6. 模型看到的内容和 Agent 执行的动作是否都有日志？
7. 任务失败后，能不能从一个明确的事件点继续？
8. 长期记忆是否可见、可编辑、可回滚？

这些能力很难在发布会上的模型跑分里体现，却更接近真实开发中的生产力。

我的判断是：**代码 Agent 的第一阶段竞争是“谁的模型更聪明”，第二阶段竞争是“谁的开发机更可靠”。**

模型会逐渐变成可替换的推理层。真正拉开产品差距的，可能是它给模型配了怎样的工具、怎样的工作区、怎样的权限、怎样的恢复机制，以及怎样把一次不可解释的自动操作变成可审查的工程记录。

## 我们能做的

如果要在自己的 Agent 工作流里提前适应这件事，不需要一开始就搭一套云端 IDE。可以先把几个基础边界补上：

- 给每个任务独立 worktree，不让并行 Agent 共用一个脏工作区；
- 把构建、测试和运行环境写成可重复执行的脚本；
- 把 Agent 的工具调用、关键输入和文件变更保存成事件日志；
- 把长期规则和项目记忆放到可 review 的文件里，而不是只存在某次对话中；
- 明确哪些凭证可以给 Agent，哪些操作必须人工确认；
- 为长任务设置恢复点，至少能知道它上一次完成了哪一步。

这些动作看起来不像“升级模型”，但它们直接决定 Agent 能不能稳定地完成任务。

未来我们比较的可能不再是“哪个 Agent 写出的代码更像人”，而是：**哪个 Agent 能在一台可控的开发机上，把任务完整、连续、可恢复地做完。**
