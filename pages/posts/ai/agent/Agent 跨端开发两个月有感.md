# Agent 跨端开发两个月有感

七八月这两个月，公司在推跨端，我把 web 前端、小程序面板、硬件开发板挨个试了一遍。试完最直接的感受是：硬件的壁垒最深，它的知识体系和我做后端积累的那套几乎不重叠，学起来最费劲。

但把三次实际产出摆在一起看，结论跟这个感受是反的。**我最没底的那个端，Agent 交付得最好；我觉得"还能接受"的那个端，我最兜不住。**

这篇想把这个错位讲清楚，因为它顺带回答了另一个我一直在纠结的问题：在这种节奏下，踏下心学一门新技术，真的比直接花钱买更强的 Agent 划算吗。

文章主题思想是我的，实际上也是 Agent 代笔。

---

## 一、三个端，我的判断和实际产出对不上

先摆事实。

**硬件**。一块 T5AI 开发板，接官方 3.5 寸屏，做一台横屏录音机：两侧实时音量条、中间录音键、30 秒上限覆盖式、录放都能暂停、外加实时分贝数字。应用层 931 行 C，SDK 一行没动，从"让屏幕亮起来"到收工不到五小时。我一共打了二十来句话，最长的一句是一段大白话需求，47 分钟后编译通过烧进去就是那个界面。中间卡死过一次，五分钟定位修好，根因是它自己写的一个整数开方函数。

这里面我没做的事：查 Kconfig 符号名、翻原理图找引脚、写 LVGL 布局、算 RMS、写状态机、配交叉编译。全是我不会的。

**前端和小程序**。我写过 Vue，跨到 React 看看还能接受，语法读得懂，组件结构看得明白。代码上线了。

但我说不太清它为什么能跑。哪些渲染是必要的、状态为什么放在那一层、构建出来多大、什么情况下会白屏 —— 这些我当时没问，现在也答不上来。它上线，不是因为我判断它可以上线，是因为它跑起来看着对。

同样是"Agent 写的、我不完全懂的代码"，硬件那次我心里踏实，前端这次我心里发虚。**踏实和发虚的分界线，不在我懂多少。**

## 二、Agent 吃的不是知识，是反馈

T5 那次顺，不是因为硬件简单。是因为那块板把硬件事实变成了 Agent 能吃的东西：

- 建工程时生成的 `board.json` 把全部外设写成结构化数据 —— 型号、接口、引脚、使能用的 Kconfig 符号、哪些是焊死的哪些要外接。不是一份 PDF 让它猜。
- 编译会报错，错误信息是确定的。
- 烧进去能看见，屏幕亮没亮、音量条跳不跳，一眼就知道。
- 连最模糊的那个"音量条反应慢"，我拿手机分贝仪一对照，就变成了可校准的数字。

四条反馈回路都是通的，所以它敢下判断、能自己验证、被 SDK 骗了也能靠实测爬回来。换一块没有 `board.json` 的板子，同一个 Agent 立刻抓瞎 —— 不是它变笨了，是它眼睛被蒙上了。

这条规律反过来也成立，而且更值得警惕。**前端的反馈回路便宜到几乎免费**：热更新一秒生效、控制台直接报错、截图就能看结果。正因为太便宜，Agent 在前端表现极好 —— 好到掩盖了一件事：

> 便宜的反馈只覆盖"现在看起来对"，不覆盖"三个月后还对不对"。

编译过了、页面渲染出来了、点了有反应了 —— 这些信号 Agent 全部拿得到，也全部满足了。而状态管理会不会失控、这次改动让首屏多加载了多少、这个组件在弱网下会怎样、半年后谁来维护，这些信号在当下的反馈回路里根本不存在。它不会漏掉它能看见的东西，它只会漏掉没人给它看的东西。

所以"Agent 在这个领域行不行"这个问题，答案基本不取决于领域有多难，取决于这个领域的验证有没有被数字化。硬件被 TuyaOpen 数字化了，所以它行；前端天然是数字化的，所以它更行 —— 但也正因为太行，容易让人跳过"哪些代价没被验证"这一问。

## 三、真正让我不舒服的是哪一点

不是"代码不是我写的"。后端的代码也有一多半不是我一个字一个字敲的，我从来没为这个不舒服过。

差别在出事的时候。

后端线上炸了，我能看日志、能顺链路、能定位到哪个方法哪个配置，Agent 只是帮我跑得快一点。前端要是炸了呢？我能做的多半是把报错贴回去，让它猜。

这里有一个我觉得挺硬的自测判据：

> **出事的时候，你是在指挥它，还是在向它求助。**

正常路径上这两者看不出区别，产出完全一样，代码一样能上线。能力只在异常路径上兑现。而软件工程的成本，绝大部分堆在异常路径上。

用这个尺子量一下我这两个月：硬件那次卡死，我至少知道现象、能描述复现条件、能拿手机做外部校准，我是在给它提供判据；前端如果出事，我只有一张报错截图。

真正的区别不在"这份能力算不算我的"，在**这份能力在异常路径上归不归零**。

## 四、后端和前端，我和 Agent 的位置调了个个儿

把这两个端的协作关系画出来，是两个方向相反的结构：

**后端**：我出方案、定边界、判断代价，Agent 补细节和样板。就算换一个能力弱得多的 Agent，只帮我查查资料，我照样能交付可用的东西 —— 慢一点而已。我的能力是地板，Agent 是乘数。

**前端**：我提供资料和需求，Agent 出方案。Agent 强，我的产出就好；Agent 弱，我基本寸步难行。Agent 是天花板，我是资料员。

产出上这两种关系可能看不出差别，两边的代码都上线了。区别在于**上限归谁**。第二种结构里，我的产出上限等于 Agent 的上限 —— 而 Agent 的上限对所有人是一样的，谁都能买到。这意味着我在这个方向上没有任何差异化可言。

## 五、那到底该学，还是该买更强的 Agent

先说结论：这题不是二选一，而且原来的问法有个隐含前提是错的。

**该买的照买，这不是对立面。** 省更强 Agent 的那点钱，是最贵的一种省法。真正稀缺的既不是钱也不是学习时间，是注意力 —— 用 Agent 省下来的那几个小时，是拿去再多交付一倍需求，还是拿去搞懂刚才交付的东西。这才是那个真正的取舍，而它跟买不买没关系。

**"学不学"这个问法要换成"学什么"。** 别去学 React 生命周期、别去背 hooks 规则、别去啃状态库 API —— 这些恰恰是 Agent 最不会出错的部分，学了也只是低配版重复它。该学的是**前端特有的代价结构和失效模式**：状态该放在哪一层、什么操作会触发大范围重渲染、构建产物多大、首屏加载了什么、什么条件下会白屏、这段代码半年后谁能改动。这些是 Agent 最容易漏、而且漏了之后最贵的东西 —— 因为它们在"跑起来看着对"的反馈回路里全都不可见。

**学的方式也变了，不需要脱产。** 每次 Agent 生成完，多问一句："你为什么这么写，有什么代价，什么情况下会崩。" 这是一次带标准答案的练习，成本是几分钟，不是几个月。这也是学习和买 Agent 唯一真正重叠的地方：更强的 Agent 不只写得更好，它解释得也更好，用它来学比用它来产出更划算。

**目标不该是"追上商业前端平均水平"。** 一是全职大概要半年到一年，兼职追不上；二是那条线本身在贬值，追上了也只是把自己推向同质化。目标应该是把后端已有的判断力延伸过去：够得着异常路径、看得懂代价、提得出对的问题。从现在到那个位置，大概是几周的针对性投入，而且这几周能被 Agent 大幅加速。

**这个差价就是整道题的答案：** 六到十二个月对上几周，而且长的那条路终点是同质化，短的那条路终点是"我能兜住我签字的东西"。

## 六、硬件那条线，反而最不该硬学

按上面这套框架，硬件的处理方式跟直觉也是反的。

它的知识壁垒确实最高，但那道墙正在被 `board.json` 这类东西一块块拆掉。真正值钱的不是我背下多少寄存器和引脚，是**"怎么把一个陌生领域的事实，整理成 Agent 能吃的反馈"** —— 这块板做对的就是这一件事，而这个能力跨端通用。

而这件事恰恰是后端出身的人有优势的：结构化数据、契约定义、把模糊问题变成可验证的判据，本来就是我们日常在干的。

## 我们能做的

1. 在每个端上找出"跑起来看着对"覆盖不到的那类问题，逐条列出来 —— 那就是你在这个端上的学习清单，通常不超过十条。
2. 用异常路径自测：这个端出事了，我是能指挥它还是只能求助它。只能求助的端，就是能力缺口所在，跟代码是谁写的无关。
3. 把每次生成变成一次带答案的练习，追问代价和失效条件，而不是只收结果。
4. 更强的 Agent 该买就买，但把省下来的时间分一部分回去理解产出，而不是全部拿去堆量。
5. 进新领域时，先花时间把领域事实整理成结构化的、可验证的东西，再让 Agent 动手。这一步的投入回报，远高于自己去啃知识。
