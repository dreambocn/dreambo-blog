# DeepSeek V4.1 Flash：速度拉满了，但交付未必更快

一句话定位：2026 年 9 月 8 日，DeepSeek 悄悄开放了一个只活到 9 月 10 日的中间版本。它不是正式发布的 V4.1，而是一个临时 API 模型：`deepseek-v4.1-flash-expires-on-0910`。

我把目前能找到的官方信息、第三方实测和开发者反馈放在一起看，得到的判断是：**V4.1 Flash 最实在的升级是原生多模态和极高的解码速度；但长任务仍然会出错，Agent 还可能因为反复验证和大量子 Agent 把等待时间与账单一起推高。**

## 先把它的身份说清楚

你给的 DataLearner 页面已经把几个关键信息标出来了：这是 DeepSeek API 平台的限时中间预览版，模型名带有 `expires-on-0910`，预计 9 月 10 日下线；调用时不需要换 Base URL，只需要把模型名换成临时 ID。

它和线上稳定的 `deepseek-v4-flash` 不是一回事。后者仍然对应 V4-Flash-0731；V4.1 只有收到内测资格的账号才能调用，而且单账号并发上限据报道是 20。也就是说，这次更像一次大规模灰度试用，不是把线上模型原地升级。

更重要的是，DeepSeek 官方公开资料目前还没有给 V4.1 Flash 发布正式模型卡、参数规模、上下文长度、独立价格表或标准 Benchmark。官方更新日志最新公开的相关版本仍然是 8 月 21 日发布的 V4-Flash-Vision-Exp，官方价格页也仍然只列出 V4-Flash、V4-Pro 和 V4-Flash-Vision-Exp。

所以本文中的“评测结果”，主要是早期开发者用 DeepSeek Harness、Claude Code 等 Agent 工具做的任务型实测，不是统一实验室在同一套数据集、同一套采样参数下跑出的标准榜单。

## 最大变化：它终于能直接看图并继续干活

之前的 V4 Flash 并不是完全不能处理视觉任务，但在一些 Agent 环境里，模型往往需要先调用 OCR、像素分析或其他图像工具，再根据工具返回的文字和数据拼出图片内容。

V4.1 Flash 的变化是直接把视觉理解放进模型本身。第三方测试者把同一张图片分别交给 V4.1 和旧 V4：一组图片描述任务，V4.1 用时约 5.7 秒，V4 用了约 200 秒；另一组任务中，V4.1 用时约 7.6 秒，旧 V4 用时约 751 秒。

这不只是“看图回答更快”。在一个根据三张参考图制作《星光邮局》小游戏的任务里，V4.1 正确保留了角色、颜色和 5×5 关卡布局，还把玩家、障碍、包裹和目标格的位置写进了游戏逻辑。旧 V4 则理解成了 7×7，角色和布局都发生了偏移。

这才是原生多模态对 Agent 的价值：

- 读网页、终端和 IDE 截图；
- 看设计稿，然后生成前端；
- 读图表，把视觉信息变成数据和交互逻辑；
- 根据执行结果截图继续判断；
- 生成图片或 SVG 后回看结果，再尝试修正。

模型不再只是“看一眼图片后写一段描述”，而是可以把图片当成工作流中的输入继续调用工具。

## 速度：输出像闪电，端到端还要看工具链

V4.1 Flash 的速度反馈非常一致。36 氪汇总的早期测试中，有开发者测到它在简单对话里约 0.3 秒开始思考，端到端耗时约 0.8 秒；另一组长文本任务的端到端吞吐达到约 409.5 tok/s。

Reddit 上一位开发者用相同的 Harness、相同的应用规格，让 V4.1 Flash 和 V4-Flash-Vision-Exp 完成同一个应用：

| 指标 | V4.1 Flash | V4-Flash-Vision-Exp |
| --- | ---: | ---: |
| 总耗时 | 18 分 49 秒 | 30 分 11 秒 |
| 总 Token | 1159 万 | 2031 万 |
| 输出 Token | 12.6 万 | 15.4 万 |
| 模型生成速度 | 361 tok/s | 120 tok/s |

这组结果里，V4.1 大约快了 38%，总 Token 少了约 43%。不过测试者也明确提醒：有些任务仍在运行，且这不是严格控制变量的实验，因此只能作为早期信号。

更完整的 14 任务对比，反而暴露了一个容易被忽略的问题：V4.1 初期输出速度约 284 tok/s，旧 V4 约 97 tok/s，但“星光邮局”小游戏最终 V4.1 用了约 34.5 分钟，旧 V4 用了约 30.5 分钟。

拆开日志后发现，V4.1 生成代码确实更快，模型工作时间约 15.5 分钟，旧 V4 约 23.4 分钟；但 V4.1 等工具运行和验证的时间约 18.7 分钟，旧 V4 只有约 6.6 分钟。

所以需要把三种速度分开：

1. 首次响应速度；
2. 模型生成 Token 的速度；
3. 从输入到最终可用结果的总耗时。

V4.1 在前两项上非常强，但第三项还取决于它调用了多少工具、启动了多少子 Agent、重复验证了多少轮。

**它是一个吐字很快的 Agent，不一定是一个每次都交付得更快的 Agent。**

## 编程能力：前端原型明显进步，但仍然需要验收

新浪科技转载的一组实测里，V4.1 Flash 用约 2 分钟生成了“鹈鹕骑自行车”的 SVG。整体结构基本正确，鹈鹕的喉囊、自行车车架和辐条都画出来了。

接着让它生成一个能旋转、缩放的 Three.js 3D 动画，模型用了约 12 分钟交付了一个包含 6 个源文件的项目。效果可以运行，但自行车把手缺失，鹈鹕的腿部结构也不自然。

更复杂的 Minecraft 风格体素世界任务中，它用了约 52 分钟完成一个约 7550 行代码的游戏，并自行生成了 53 个 Node.js 单元测试和 38 个浏览器集成测试。测试者还称模型进行了代码审查，发现并修复了 15 个 Bug。

这个结果很能说明 V4.1 的特点：它不满足于“写完代码”，会主动测试、检查和修复。但它仍然不是可以不验收的自动程序员。更复杂的“怪兽城市大战”任务，测试者等了两个多小时仍未完成。

在实际开发里，最值得期待的是它对以下任务的帮助：

- 截图驱动的页面修复；
- 根据设计图生成可运行前端；
- 复杂交互原型和小游戏；
- 代码、测试、浏览器验证一体化执行；
- 需要不断看执行结果再修改的任务。

但最终验收仍然要落到浏览器行为、单元测试、边界输入和人工视觉检查上。模型自己说“已经完成”，依旧不能当作完成证明。

## 长上下文：能读很多，不代表能一直记对

长文本测试没有展示出同等幅度的提升。

一位测试者让 V4.1 和旧 V4 各写一部约十万字的网文。V4.1 写了约 10.67 万字、25 章；旧 V4 写了约 9.74 万字、51 章。V4.1 的细节更多，但节奏更慢，测试者还发现它把同一个扫地动作的次数写乱了。

另一个 A 股历史回测报告任务中，V4.1 生成的 13 张图表都能加载，但报告首页写年化收益 15.1%，图表中却出现 17.8%，总收益和最大回撤也没有统一。

这类错误不是“模型完全不会做”，而是全局一致性没有跟上输出能力：它可以完成长文、生成报告、做出图表，却没有始终保持同一套数字、章节状态和事实约束。

因此，1M 上下文更适合被理解为“可以放进去更多材料”，而不是“放进去之后模型就能完美维护所有细节”。长上下文应用仍然需要：

- 把关键事实抽取成结构化状态；
- 对数字和枚举做程序化校验；
- 对长文分段生成并维护摘要；
- 对最终报告做交叉引用检查；
- 用固定回归集重复测试，而不是只看一次 Demo。

## 便宜是真的，但复杂 Agent 可能更烧钱

V4.1 内测沿用 V4 Flash 的价格。9 月 10 日价格调整前，空闲时段每百万 Token 的价格大约是：缓存命中输入 0.05 元、缓存未命中输入 1.5 元、输出 4.5 元；高峰时段为两倍。

新浪报道的一组测试很夸张：包括一个未完成的长任务在内，1.56 亿 Token、825 次 API 调用，总费用约 1.93 美元，折合人民币约 13 元。这个数字看起来非常便宜，但不能直接拿来推算所有任务，因为其中缓存命中占比很高。

更值得注意的是另一组 14 任务对比：V4.1 累计约 3 亿 Token，缓存命中率约 98.9%，消费 61.96 元；旧 V4 消费 45.47 元。V4.1 反而贵了约 36%。

原因是它在复杂任务中更倾向于启动子 Agent：大型游戏任务启动了 13 个子 Agent，V4.1 用了约 1.21 亿 Token，旧 V4 约 3653 万；游戏和小说两个任务合计启动了 37 个子 Agent，仅这些子任务就消耗了一亿多 Token。

并行和自检当然有价值，但每个子 Agent 都可能重新读取材料、生成中间结果、执行检查，主 Agent 最后还要整合和返工。这些“看不见的工作”都会进入账单。

所以不能只看模型的标价，应该看完整任务成本：

> 图片 Token + 重复上下文 + 输出 Token + 子 Agent + 工具调用次数 + 人工返工时间。

9 月 10 日起，Flash 系列还会继续降价：缓存命中输入从 0.05 元降到 0.02 元/百万 Token，缓存未命中输入从 1.5 元降到 1 元，输出从 4.5 元降到 4 元；高峰时段仍是空闲时段的两倍。价格变便宜后，V4.1 的复杂 Agent 习惯会不会导致更多调用，反而更值得观察。

## 它能不能替代 V4 Pro

目前不能下这个结论。

DeepSeek 内测反馈问卷里据报道直接问了测试者：“你觉得这个模型能全面替换线上的 DeepSeek V4 Pro 吗？”这个问题本身说明，DeepSeek 似乎在探索 Flash 是否能覆盖更多原本属于 Pro 的 Agent 任务；但它不是 V4.1 已经全面追平 Pro 的证据。

现有测试更支持下面这个判断：

- 视觉理解和视觉编码：V4.1 明显强于旧 V4 Flash；
- 单轮或短任务速度：V4.1 非常快；
- 普通数据处理和报告工程：与旧 V4 接近，未见全面跃升；
- 非视觉 Agent 的端到端耗时：不一定更快；
- 长文一致性：仍然会出现数字和状态错误；
- 复杂 Agent 成本：可能因启动子 Agent 和验证流程而增加。

它更像是“Flash 级价格、Pro 级野心”的实验，而不是一个已经用公开标准证明自己可以替代 Pro 的正式版本。

## 现在值得怎么用

如果你有内测资格，V4.1 Flash 值得立即放进自己的测试集，尤其是下面几类任务：

- 图片、截图、图表输入后生成代码；
- 浏览器或终端 Agent；
- 需要看执行结果再继续修改的前端任务；
- 大量但单次失败代价不高的视觉抽取；
- 低成本验证多模态产品想法。

但接入方式要保守一点：把临时模型名放在独立配置项里，保留 `deepseek-v4-flash` 的一键回退，不要因为一两次 Demo 成功就替换线上默认模型。内测模型的接口、行为、限流和下线时间都不稳定。

测试时至少记录这几个指标：

- 任务是否真正完成；
- 首 token 延迟和总耗时；
- 工具调用等待时间；
- 总 Token、缓存命中率和子 Agent 数量；
- 测试是否由模型自己生成，还是由独立测试程序执行；
- 最终结果需要人工返工多少。

## 我们能做的

V4.1 Flash 目前最适合被当作一个低成本多模态 Agent 实验场，而不是无条件的生产替代品。

如果任务是“看图、写代码、跑起来、再根据截图修一轮”，它很可能是目前最值得试的 Flash 模型之一；如果任务是“长时间自主运行、数字必须前后一致、失败代价很高”，就要给它配回归测试、预算上限、超时和人工审核。

真正有价值的对比不是问“它是不是比 GPT、Claude 或 Pro 强”，而是拿自己的真实任务做 A/B：同一份需求、同一套工具、同一台开发机，比较最终交付质量、总耗时、总 Token 和人工返工。

DeepSeek V4.1 Flash 这次最重要的信号，不是它在某个榜单上多了几分，而是它把视觉输入、代码生成、工具执行和自我验证放进了同一个低价 Agent 循环里。

只是这个循环现在还有一个副作用：**模型变得更快、更勤奋，也更容易把任务做复杂。**
