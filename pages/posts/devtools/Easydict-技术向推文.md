# Easydict：macOS 下的多引擎聚合翻译客户端

## 概述

Easydict 是一个开源的 macOS 词典与翻译客户端，由 tisfeng 开发。核心设计是**聚合层**——它本身不提供翻译能力，而是把 20+ 个翻译后端统一到一套查询接口和一个结果视图下，用户在同一次查询中并排比对多个引擎的输出。

- 仓库：https://github.com/tisfeng/Easydict
- 协议：GPL-3.0
- Star：14.2k / Fork：718
- 主要语言：Swift（早期为 Objective-C，仍有遗留）
- 系统要求：macOS 13.0+（12 及以下停留在 2.7.2）
- 分支策略：`main` 为稳定发布，`dev` 为开发分支

## 功能构成

### 1. 输入源（四种取词通道）

| 通道 | 默认快捷键 | 说明 |
|---|---|---|
| 输入翻译 | `⌥ A` | 唤起悬浮输入框，回车触发查询 |
| 划词翻译 | `⌥ D` | 选中文本后快捷键触发；也支持选中后自动浮出查询图标 |
| 截图翻译 | `⌥ S` | 框选屏幕区域 → OCR → 翻译 |
| 静默截图 | `⌥ ⇧ S` | 框选区域 → OCR → 结果直接写入剪贴板，不弹窗 |

静默截图这条通道值得单独说：它把 OCR 从"翻译流程的前置步骤"解耦成了一个独立的屏幕取文能力，处理扫描件 PDF、图片型文档、无法选中的 UI 文本时，实际使用频率可能高于翻译本身。

### 2. 后端矩阵

- **系统能力**：Apple 系统词典、Apple 系统翻译（macOS 原生翻译框架）
- **传统机翻**：DeepL、Google、Bing、有道、腾讯、百度、小牛、彩云、阿里、火山
- **LLM**：OpenAI、Gemini、DeepSeek、Groq、Zhipu AI、GitHub Models、豆包
- **本地推理**：Ollama

Ollama 这一项决定了它的隐私上限——配合内置 OCR，理论上可以走一条完全不出网的链路：本地截图 → 本地 OCR → 本地模型翻译。对处理内部文档的场景是有意义的。

接入 Apple 系统词典也不是可有可无的加分项：LLM 和机翻给的是"译文"，词典给的是"释义、词性、例句"，这两类结果的用途不同，能在同一个结果面板里同时拿到，减少了工具切换。

### 3. 其他

自动语言识别、48 语种、多 TTS 发音源。

## 安装

```bash
brew install --cask easydict
```

或从 Releases 直接取包：https://github.com/tisfeng/Easydict/releases

首次启动需要授予屏幕录制（截图 OCR）与辅助功能相关权限，这是划词类工具的常规要求。

## 使用评估

**可用性：达标。** 后台常驻的资源占用没有可感知的异常，快捷键响应无明显延迟，OCR 识别质量在中英混排的截图上表现稳定，二次校对的需求不高。多引擎并排输出这个交互决策是整个产品最有价值的部分——机翻负责保证语义不跑偏，LLM 负责让译文通顺，两者放在一起由使用者裁决，比单引擎黑盒输出更可靠。

**主要不满：界面设计。** 这是我对它唯一明确的负面评价，且属于设计层面而非工程层面：

- 结果面板采用卡片纵向堆叠，启用的服务一多，单屏信息密度过高，需要滚动才能看完一次查询的结果，削弱了"划词即看"的即时性；
- 视觉层级偏弱——词典释义、机翻译文、LLM 输出这三类性质不同的结果，在样式上区分度不够，扫读时需要额外的认知成本；
- 整体观感偏"功能陈列"而非"信息设计"，排版和配色的完成度与同类商业产品有差距。

这些是主观判断，且对一个个人维护的免费开源项目做审美苛求并不公平。工程侧的完成度是没有问题的。

## 结论

如果需求是「功能覆盖全、可自由接入自有 API Key、支持本地模型、零成本」，Easydict 是当前 macOS 上综合性价比最高的选择之一，建议直接部署。如果对界面质感有较高要求，需要接受它在这一维度的短板。

对我而言功能价值高于界面成本，它仍在我的登录项里。
